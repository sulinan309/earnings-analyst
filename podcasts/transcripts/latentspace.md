# Latent Space:从 0 到千万用户——OpenAI Akshay Nathan 谈 ChatGPT Work 与 Codex(内容纪要,非逐字转录)

**播客:** Latent Space
**日期:** 2026 年 7 月 28 日
**嘉宾:** Akshay Nathan —— OpenAI"生产力(Productivity)"团队负责人,主导 ChatGPT Work 的发布;2023 年加入 OpenAI,此前曾在企业级 ChatGPT(ChatGPT Enterprise)团队;更早在 Airtable、以及一家做 AI 自动化测试的创业公司工作过(押注"把代码的威力交给不懂代码的人",在 LLM 出现前效果有限,LLM 出现后他认为这正是补上的那块拼图)。
**主持:** Latent Space 主播 + 联合主持 Vibhu

> 说明:本期是一次产品方法论访谈,信息密度高但偏对话式、少硬数据。这次采用**主题式摘要**、以转述为主,原话引用控制在最小范围。

## 一、ChatGPT Work 的起源:Codex 内部意外走红,催生了"合并"的决定

Akshay 说,推动 ChatGPT Work 诞生的关键契机,是 Codex 发布后在 OpenAI**内部非工程岗位**中出现的意外采纳——他在做用户调研时发现,战略财务、市场等非技术团队的同事不仅在用 Codex 完成本职工作,更让他印象深刻的是,这些人对"自己在用 Codex"这件事**感到自豪**,一种"我抢先用上了新东西""我有了超能力"的心态。这让团队意识到:agent 的能力早于预期就能扩展到非开发者身上,而 OpenAI 已经握有 ChatGPT 数以亿计的庞大用户基础——问题变成"怎么把这种能力真正带给他们",这个产品命题最终演变成了"Super App"式的合并策略,并落地为 ChatGPT Work。

## 二、Codex、ChatGPT、Work 三者的底层关系:同一套 harness,不同的产品外观

一个关键的技术澄清:**Codex 和 ChatGPT Work 背后是同一套 harness(工具编排层)**,团队针对"知识工作"场景(插件、计算机操作、artifacts 等)做了专门优化,这些能力在两个产品里都能拿到。差异主要在**产品层面的克制取舍**——比如 Codex 模式里会暴露 git diff、文件改动细节等偏"开发者视角"的信息,Work 模式里则不展示这些。团队的产品哲学是:**不希望用户被迫"选择自己在哪个体验里"**——这被 Akshay 类比为"通用人工智能不该让人先选择用哪个版本的 AGI",理想状态是模型自己决定用什么方式服务你。据介绍,系统里已经有一个"路由决策"机制:如果你在传统 ChatGPT 对话里提出的需求更适合 Work 模式处理(比如要生成一个电子表格),模型会引导你切换过去。

Akshay 还做了一个简短的"harness 口述史":经典的 ChatGPT harness(为对话、搜索、学习等场景优化,注重延迟和"人格"打磨)服务了从 o1 时代至今的产品;而 Codex 团队发现,如果给 agent 一个"无限灵活的计算机环境"作为操作对象,能做到的事情量级完全不同——于是团队判断,知识工作场景更适合"计算机环境"这套范式,即用 Codex 的 harness 逐步取代经典对话式 harness,两者目前处于交叠过渡期。

## 三、企业级 AI 落地的老问题:"千人千面"的需求 vs 缺乏具体使用场景

Akshay 回顾在 ChatGPT Enterprise 团队的经历:企业客户对"要用 AI 做什么"往往给不出具体答案——如果直接问"你想用 AI 做什么",得到的多是笼统套话;但如果问"你想让 AI 解决哪个具体任务",答案会极度发散、五花八门。他认为这正是企业级 AI 推广的核心难点所在:模型本身"什么都能聊"是魔法,但这也意味着用户经常不知道该拿它做什么。他把这个问题的解法总结为"到用户所在之处迎接他们"——不是空谈能力,而是先搞清楚具体场景,再手把手教会怎么用 AI 撬动杠杆。他区分了这和"前置部署工程师(forward-deployed engineer)"模式的关系:后者偏市场/服务侧,而产品本身也必须做对——最终无论方法论多完善,用户面对屏幕时,产品要负责把他们引导到正确的地方。

## 四、当前企业 AI 落地的阶段判断:早期采用者已经"顿悟",大多数人还没到那一步

Akshay 认为,目前存在一小群早期采用者已经真正理解"只要上下文对、工具接对、有人监督,agent 几乎什么都能干";但还有一个规模大 10 到 100 倍的群体尚未意识到这一点。他判断这是 ChatGPT Work 想要争取的下一波市场空间。

## 五、"生产力"团队为什么不叫"企业"团队

Akshay 解释团队命名逻辑:之所以叫"生产力(Productivity)"而不是"企业"或"工作",是因为团队认为 ChatGPT Work 的边界并不局限于严格意义上的"工作"——他举了一个用户案例:有人收到快递照片但没找到包裹,让 ChatGPT Work 去分析照片、比对小区周边信息,最终定位到了具体的公寓楼。这类"个人生活相关但体现出高度自主性"的任务,正是团队想覆盖的范围。

## 六、模型与配置的选择建议:默认设置对多数人已经够用

面对"该用 Ultra 模式还是普通模式、什么时候上 sub-agent"这类"配置调参式"的问题,Akshay 的建议是:**团队刻意把默认配置调成对大多数人已经最优**,只有当默认配置在效率或质量上不够用时,才需要手动切换到其他配置(比如更强的推理档位、或不同模型档位)。他承认目前面向高阶用户暴露的选项可能偏多,团队也在着手简化。

关于何时用 multi-agent(比如"Ultra"模式或多 agent 并行):比较适合"高度复杂/开放式探索"或"可高度并行拆分"的任务;而"可以持续、可验证地稳步推进"的任务用单 agent 模式("Goal"模式)效果更好——但他坦言大多数任务其实两边都不完全占,所以还是建议先用默认设置试试,再按需调整。

## 七、Sites(生成式网页/artifacts):正在取代 PPT 和电子表格的协作载体

这段是本期比较具体的产品洞见。团队在这次发布中重点投入了 "artifacts"(内部代号,产品里不会直接用这个词对用户说)能力——既包括模型侧(如从 5.4 到 5.5、5.6 版本间生成质量的显著提升),也包括产品侧的用户体验(比如生成可托管的网页,不再需要用户自己搭建)。

Akshay 分享了一个内部案例:公司财务团队原本每月用 PPT/Excel 做汇报,现在直接改用"Sites"(AI 生成的可交互网页)作为团队协作载体——原因是 PPT、Excel 这类工具虽然功能强大,但总有"人不知道怎么用某个功能"或"工具本身做不到"的边界;而用自然语言直接向 AI 描述需求生成的网页,理论上"你想要什么都能生成"。两位主持人现场做了对比实验(一人用 ChatGPT Work 处理了大量截图输入 + 消耗约 17 亿 token,另一人用 Codex 花约 19 分钟),分别为一款桌游生成了带 3D 交互的可玩网页、以及用于展示"AI 自我对弈训练"实验结果的研究面板。双方都认为这类"网页作为研究/汇报产出物"的形态,比传统 markdown 或幻灯片信息密度更高、也更灵活,但目前普遍存在**内容冗长、需要反复精简**的问题。

Akshay 提到,他们在内部也把这种"生成式网页"用作产品早期原型/设计协作工具——比如本期提到的那个"模式选择滑块(slider)"UI 组件,就是设计、工程、产品团队在一个 Sites 里协作打磨出来的。

## 八、工作与生活的边界正在模糊

多位对话者认同,ChatGPT Work/Codex 正在让"工作相关"和"个人生活相关"的使用场景彼此渗透——个人用它做健身计划、备餐规划、玩桌游 AI 训练,却常常无意间把这些"玩具级"用例展示给同事,反而成了最有效的产品传播方式("show, don't tell",亲眼看到别人做到了什么,比任何教程都有说服力)。Akshay 提到,团队内部一个有趣的用例是"自动侦测团队 Slack/文档里的热梗、定时生成表情包发到共享频道"——他认为这体现了模型除了"有用"之外,也开始展现"意料之外的联想能力"(能发现你自己都没想到的关联),这种能力未来会延伸到更严肃的场景。

## 九、发布数据与产品定位:10 万到千万用户,但"这只是开始"

Akshay 表示,ChatGPT Work 是他经历过的最成功的发布之一(甚至认为比 GPT-5.0 发布更有个人成就感),用户数已达到千万量级。但他强调这在 ChatGPT 数亿用户体量面前"仍只是起步"——目前 Work 仅对付费用户开放,且不会默认把用户导入(需要引导用户理解产品价值)。他透露 Codex 作为独立品牌会长期保留,团队没有打算"取代"它——开发者一直是 OpenAI 的核心市场,Codex 未来会继续为软件开发场景做专门优化,合并只是让用户能在"写代码""生成文档""搜索"等任务间无缝切换,而不是削弱开发者体验。

关于内部术语是否会渗透进普通用户认知:他举例说没人会说"给我生成一个 artifact",用户只会用自己熟悉的语言描述需求(比如"帮我做个 PPT"),这正是团队希望达到的效果——工具应该隐形,而不是让用户学习新黑话。

## 十、OpenClaw 的启发:个人 AI 操作系统的雏形

Akshay 分享了自己和太太搭建 OpenClaw(一个开源的个人自动化 agent 项目)来管理家庭事务的经历(比如自动创建日历事项),他认为这段经历给 ChatGPT Work 的设计带来了不少启发——尤其是"持久化计算机环境"(文件在多次会话之间持续存在)这个理念。他提到团队内部有成员已经完全把原来用 OpenClaw 做的事(健身计划、指甲护理提醒等个人事务)迁移到了 ChatGPT Work 上,因为底层原语(定时任务、文件系统访问、跨时间引用记忆)是相通的。他判断两者会长期并存、互相借鉴,而非谁取代谁——ChatGPT 的用户认知度远高于 OpenClaw,如果 ChatGPT Work 能把 OpenClaw 证明有效的那些"魔法"带给更多人,本身就是一种成功。团队对 Work 的核心产品哲学是:用户进来开始一次对话/会话,理论上应该能就地完成任何事情,而不需要跳转到其他入口去调用某个具体功能。

## 十一、记忆系统:从"经典 ChatGPT 记忆"到 Memory V3、以及实验性的 Chronicle

Akshay 认为记忆是用户最认可 ChatGPT 的地方之一——"感觉这就是专属于我的 ChatGPT"是身边朋友家人最常提到的喜爱点。ChatGPT Work 复用了此前发布的 **Memory V3** 系统,让"个人记忆"在从经典 ChatGPT 迁移到 Work 时能够延续,而不是从零开始。他坦言记忆本质是个检索问题——既要"知道关于你的事",又要有足够的分寸感("EQ"),在合适的时机主动调用这些信息,而不产生负面的意外(比如说错话),这是一个公认很难、但被团队认为极其重要的方向。

他还提到一个仍处于实验阶段(默认关闭)的功能 **Chronicle**——它能从用户的电脑使用行为中学习,作为记忆系统的额外输入源,更侧重"从长期使用中提炼洞察"而非单纯问答式记忆。

## 十二、关于用 AI 写团队评审(review)的边界

主持人提出一个管理者视角的敏感问题:用 AI 生成对下属的评价是否合适。Akshay 明确区分了两件事:**绝不会**直接用 AI 生成的文字原样当作对某人的评价发出去;但会用 AI 做"上下文收集"——比如整理某位同事这段时间做了哪些贡献、哪些是自己可能没注意到的亮点(代码提交记录、Slack 讨论、评审记录等),本质上是一种更强大的"agentic 搜索"。他强调,正因为现在每个人靠 AI 能完成的工作量呈几何级数增长,管理者也必须借助同样的工具才能跟上、才能不遗漏重要信息——但最终呈现给当事人的评价文字,仍然必须由人来写。

## 十三、如何衡量"生产力"提升:旧的代理指标正在失效

Akshay 认为这是整个行业都还没解决的难题。传统上大家用"代码提交量""故事点数"等代理指标衡量效率,但这些指标和 AI 时代下"团队是否真正实现了目标"的相关性正在减弱(比如 token 消耗量、模型调用次数,都不再能可靠代表团队是否朝目标推进)。他坦言 OpenAI 自己也没有彻底解决这个问题,但提出了一个他认为很关键的管理框架:**区分"运动(motion)"和"进展(progress)"**——现在的工具让"看起来在动"变得空前容易,但真正的进展需要团队对"到底想达成什么"保持清晰、审慎的定义;如果没有这种明确性,团队很容易把"忙碌"误当成"推进"。他给团队/管理者的具体建议是关注"击球次数"的质量而非单纯数量——即团队能否高效、完整地走完"想法→构建→获取反馈→验证或推翻假设→进入下一个想法"这个循环,并在反复经历这个循环的过程中保持团队的谦逊心态与投入热情。

## 十四、团队与角色的演变:模糊的职能边界、"T 型人才"假说

关于"AI 会不会让某些岗位彻底消失"这类流传甚广的调侃式预测(比如"未来科技行业只剩四种工作"这类说法),Akshay 的判断更温和:他认为多数人会变成"T 型人才"——AI 让每个人都能在多个领域触达"通才"级别的产出(比如他自己虽然不是设计师,也能借助 AI 迭代出像样的设计方案),但每个人依然会保留一个自己真正深耕的专长领域,在这个专长上借助 AI 走得更深。他认为团队真正的瓶颈正在从"人力/技能"转移到"**想法和判断力(taste)**"——因为构建的门槛已经如此之低,以至于"有多少值得做的好想法"成了新的限制因素,而好的想法很少凭空产生,往往来自和用户的持续对话、对真实摩擦点的观察、以及在已有基础上的迭代——这也是他认为"通才型、能闭环整个反馈循环的人"会持续有价值的原因。
